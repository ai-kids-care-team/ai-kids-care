# analyze-experience — 用户与功能视角审查方法

从**真实使用者**立场审查，只回答「作为使用者，我的任务办成了吗」。每条结论按 `component-analysis-orchestrator` 的 finding schema 输出（id 前缀 `UX-`），severity 按**用户影响**定标。

## 为何这样审（原则）
使用者不在乎代码为什么坏、架构多优雅——他只在乎**自己的事办没办成**。一个技术上「low」的小问题，若它让家长根本收不到孩子的告警，对用户就是灾难。这个由外向内的视角能抓住技术角度容易漏掉的东西：后端做好了功能却没接到界面、界面在却悄悄失效、关键流程缺一环。**你不评判实现，只评判结果。**

## 走查清单（按本工程的角色与承诺）

### 1. 角色化旅程（对每个角色列核心任务，逐一判 happy / 失败路径）
- **家长**：注册→绑定孩子→登录→看检测告警→读通知→看感谢信。哪一步断？
- **教师**：登录→看本班检测事件→复核→发感谢信/公告。
- **园长（KG_ADMIN）**：审批注册→管班级/教室/摄像头→看本园。
- **平台 IT 管理员 / 超管**：跨园管理、系统/模型配置。

### 2. 功能完整性（三类缺口）
- 后端有能力却**无前端入口**：查 `frontend/src/services/apis/` 与页面，是否有后端端点无任何前端消费者（如通知收件箱）。
- 入口在但**坏**：实时墙是否真出画面、公告置顶编辑后是否保留、表单提交是否真生效。
- 关键功能**缺失/空壳**：密码重置、忘记账号等是否可用还是占位。

### 3. 流程连贯性
- 注册→审批→登录→使用 是否顺，中途有无死胡同。
- 告警→复核→家长通知 这条核心闭环，用户端是否真能感知到结果（不只是后端跑通）。

### 4. 反馈可理解性
- 错误提示是否人话、是否给出路；空状态/加载态/失败态是否处理；有无**静默失败**（用户以为成功实则没保存）。

### 5. 价值兑现
- 平台承诺「实时检测异常 + 及时通知家长」（见 README/spec），使用者实际是否拿得到。

## 手法
- 读 `frontend/src/app`（路由 = 有哪些入口）、组件状态（空/错/加载如何处理）、`README*.md` 与 `openspec/specs`（承诺了什么）。
- **不读后端实现做评判**——「这入口背后接通没、字段对不对」SendMessage 问 `integration-analyst`。
- 把每条写成「用户想做 X → 实际发生 Y → 期望 Z」，并按对用户的阻断程度定 severity。

## 协作
背后接通性/契约 → `integration-analyst`；前端坏味技术因 → `quality-analyst`。完成写 `_workspace/experience_findings.md` 并通知 lead（附 top-3 用户旅程断点）。
