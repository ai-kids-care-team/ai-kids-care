# ADR-0008: Language Governance（语言治理）

## 状态（Status）

Accepted

## 背景（Context）

项目协作环境存在多语言压力，需要一套**长期可维护、防漂移、面向多 Agent** 的语言治理策略。

**事实（来自负责人确认）：**

- 知识库与架构/技术决策主要由负责人以**中文**完成；当前与可预见的将来，**负责人是唯一维护者**（兼监督者角色）。
- **产品终端 UI 必须为韩语**（面向韩国幼儿园用户），且**日后有多语言 UI 计划**。
- 代码、API 路径、数据库对象天然为英文。
- 项目将使用多个 AI Agent（Claude、Codex、Cursor、Gemini 等）协作。
- 负责人**具备韩语校对（proofreading）能力**，但**不偏好以韩语读写**——故以中文为读写工作语言，韩语作为「可由本人校对定稿」的产出语言。

**推断 🔶：** 团队规模已收缩、现以单人 + AI Agents 维护，故韩语**阅读**需求当前近乎潜伏；但 glossary 的中/韩/英对照对产品 UI 与未来协作者仍有价值。

**核心约束与张力：** 同时要求「不维护多份语言知识库 + 不漂移 + 低维护成本」在数学上排除了「N 种语言各自人工维护」（N×M 维护量且必然漂移）。因此 **Source of Truth 必须单一，其余语言只能是派生视图**。

> 既有约定（✅ 已在仓库实践）：正文简体中文、技术术语保留英文、标识符保留代码原形、`product/glossary.md` 已为中/韩/英对照。本 ADR 将其形式化，并扩展到多 Agent 协作与产品 i18n。

## 决策（Decision）

采用**三层语言模型（Three-Layer Language Model）**，并据此规定各场景的语言角色。

### 三层语言模型

1. **Skeleton（骨架，语言中立，永不翻译）** — 代码标识符、DB 表/列/枚举/值、API 路径与方法、文件路径/命令/env、ID（`ADR-XXXX`、`OQ-<域>-<n>`、`RULE-XXX`、i18n 消息键）、frontmatter 键、专有技术名（Spring Boot、Neo4j、VideoMAE）。任何语言版本中一律保留原形——它是**跨语言、跨 Agent 的 join key**。
2. **Body（单一 SoT）** — 唯一被引用、被信任的层。
3. **View（派生 / 本地化）** — 见各轨道规则。

### 语言政策（规范条款）

**§1 范围与分层** — 治理四类对象，规则各异：**(A) `docs/` 知识库**、**(B) 根级 Agent 指令文件**、**(C) 产品 UI i18n**、**(D) 代码注释与 commit message**。共享骨架层。

**§2 知识库（A）语言规则**

- SoT 唯一且为**中文（中英混合：中文母句 + 英文术语/标识符）**。
- frontmatter `lang_sot` 缺省 `zh`，仅当某篇由非中文维护者主理时显式改写（机制保留以备团队构成变化，非当前需要）。
- 同一文档正文不得混入第二种叙述语言（骨架除外）。

**§3 知识库翻译规则**

- 任何非中文版本**按需即时生成**，**不入库、不被任何文档/决策引用、用完即弃**；无 provenance、无需可复现。

**§4 术语表（受控词表）**

- `docs/product/glossary.md` 为唯一**中/韩/英**三语并列受控词表。
- **术语锚点**：优先用 `代码载体`（标识符）作为语言中立锚；无代码载体的纯概念用稳定 ID `TERM-<n>`。
- KB 即时翻译、UI 文案、Agent 产出涉及领域术语时**必须命中 glossary**；缺词者**先补三语条目再使用**，禁止即兴造词。

**§5 产品 UI i18n 轨道（C）**

- **消息键语言中立**（属骨架层）。
- **`zh` = 作者参考**（便于维护者校意，推荐非强制）；**`ko` = 必出货、发布权威**语言；**日后多语 = 增量 locale**，各自为其语言权威。
- **`ko` 生成与定稿**：由 `zh` 参考经 AI 翻译（绑定 glossary）生成，再**由负责人发布前校对定稿**——韩语质量由本人校对保障，非 AI 黑箱。
- **每个 shipping locale 是发布资产**：入库、随版本维护，**不适用 §3「派生即可弃」**。
- 各 locale 领域术语绑定 glossary。
- **i18n 机制选型（库/文件格式/静态导出方案）另起 ADR**（见 OQ-LANG-6）；本 ADR 只固定语言角色。

**§6 多 Agent 规则（B）**

- **单一规范 Agent 指令源**为本仓库 `.agents/AGENTS.md`（中文）；根目录 `CLAUDE.md` 通过 `@.agents/AGENTS.md` import 指令引用该文件（Claude Code harness 展开），`AGENTS.md` 为含 import 指令的最小指针文件；两者均为真实文件而非软链，任何平台 clone 后开箱即用；`.cursorrules` / `GEMINI.md` 等若引入，须为**精简派生或指针**，禁各自扩写以防内容分叉；语言规则带英文 ID（`RULE-LANG-01`…）。
- Agent **产出 / 编辑**语言 = 目标文件 `lang_sot` 或 locale；**对话 / 回复**语言跟随人类用户（当前中文）。
- Agent **不得**：翻译骨架集、绕过 glossary 造词、把新决策写成非中文塞入 KB、把 i18n 之外的可弃派生当作真相引用或手改。

**§7 执行与变更**

- 以 `.agents/AGENTS.md` 的 Agent 规则为主要约束手段（适配单人 + Agents 现实），CI 从轻。
- **唯一硬门禁**：发布前 `ko` locale 对所有消息键**完整且经负责人校对定稿**（缺键或未校对阻断发布）。
- 本策略重大变更须经新 ADR，不得悄改。

**§8 代码注释与 Commit Message**

- 新增**代码注释**尽量使用英文（既有韩文注释作为历史保留）。
- **Commit message** 尽量使用英文。

## 后果（Consequences）

- **正面**：
  - **维护成本最低** — KB 单源 + 译文即用即弃 + 靠 Agent 规则而非重 CI，匹配单人仓库。
  - **一致性强** — glossary 受控词表 + 骨架 ID 作为跨语言/跨 Agent/跨轨道的共同锚，从源头防三类漂移（SoT 漂移、术语漂移、配置分叉）。
  - **多 Agent 可协作** — 单一指令源防配置分叉；产出/对话语言规则消除产出语言混乱，并把多 Agent 变为按需翻译的产能。
- **负面 / 代价**：
  - 出货韩语 UI 由负责人在发布前**校对定稿**，质量有保障；代价仅为校对工时。〔原 RISK-KO-QUALITY 已撤销——负责人具备韩语校对能力，该质量风险不成立。〕
  - 韩语读者读 KB 依赖按需即时翻译（无离线浏览/检索）——在当前读者 ≈ 0 的前提下可接受；若未来出现固定韩语协作者，应重评是否物化最小韩语集。
- **影响范围**：`docs/` 全库写作约定、根级 Agent 指令文件、产品前端 i18n、所有参与的 AI Agent。

## 考虑过的备选（Alternatives Considered）

- **多语言并行 KB（每篇人工维护中/韩/英）** — 未采用：N×M 维护量且必然漂移，直接违反「不维护多份知识库 + 不漂移 + 低成本」。
- **英文优先 SoT** — 未采用：在最高风险内容（决策）上以非母语写作抬高出错率，且团队不擅长长篇英文；读者收益可由廉价按需译文替代。
- **纯按需翻译、不建受控词表** — 未采用：缺少术语锚则跨文档/跨 Agent 术语漂移（同概念多种译法），破坏一致性与检索。
- **韩语优先 SoT（因终端用户为韩语）** — 仅在产品 UI 轨道采纳（`ko` 为出货权威）；KB/决策轨道不采纳，因维护者为中文。这体现「按场景而非按语言偏好」决策。
